# 执行链路：派工、证据、验收与收尾

本次改动把工作单的执行结果与模型会话的结束分开，适用于现有单服务 ARTEX 调度器。它没有实现跨设备 Hub、执行租约或多服务共享数据库的安全运行机制。

## 工作单与依赖

`add_intent` 支持 `contract`，包含 `goal_ids`、`hypothesis`、`acceptance`、`depends_on`、`direction_key`、`novelty`、`resource_key`、`budget_seconds`。批量最多四项。省略验收条件时，以 summary 作为默认验收项。

- 父节点、资产锚点与意图在同一事务中写入，错误不会留下半张工作单。
- 相同方向键、假设、资产、目标、前置和输入证据版本返回已有工作 ID。未提供方向键时只进行规范化 summary 的精确去重，不保证语义去重。
- 依赖只能指向已经存在的本任务意图，天然不能形成新节点回指未来节点的循环。未满足依赖时处于 `waiting`，不占执行槽。前置失败、被删除或未完成时不会自动解锁下游。
- `done` 表示该工作已经完成验收，可能包含证伪（negative）结果。下游仍须读取实际结果，不能把前置完成当作假设成立。
- 同一任务、同一非空资源键的工作串行执行，普通领取与人工会话续跑共用数据库准入检查。互斥不覆盖任务外进程或其它任务。
- 调度查询不再只扫描最前面的 20 条；暂不可运行的高优先级工作不会遮挡后面的独立工作。等待每十分钟增加一档优先权，最多增加十档。
- `retry_intent` 允许 Planner 对 blocked/exhausted 工作明确续做一次，必须说明依据和接续点。重复失败应等待新证据或人工处理。人工重跑接口保留原行为。

## 执行结果

Worker 启动时读取合同、直接父证据索引和依赖 ID；详情按需调用 `node_detail`。单工作预算与 Worker 配置、任务剩余期限取较小值。

Worker 先通过 `record_fact` 或 `report_finding` 保存证据，再用 `node_detail` 获取节点的 `evidence_version`，最终调用 `complete_intent`：

```json
{
  "outcome": "succeeded",
  "summary": "经过验证的结论及边界",
  "satisfied": ["与合同 acceptance 一致的验收项"],
  "evidence_refs": [{"node_id": 123, "version": "节点内容指纹"}],
  "remaining": [],
  "checkpoint": "已完成步骤及可接续位置"
}
```

可用结果为 succeeded、negative、reused、incomplete、blocked。前三种须提供有效证据引用、满足全部验收项且没有剩余项；后两种须说明剩余工作或阻塞原因。提交与运行结束时都核对执行代次和证据内容版本，过期执行者不能回写当前代次。没有提交有效结果的新工作单会进入 blocked；单纯输出“完成”不能通过验收。旧版无合同工作单继续兼容历史结算行为。

内容指纹表示探索节点的 kind、state、payload，作用是发现内容变化。它不是对原始网络流量的签名，也不能判断证据在语义上是否充分。逐字核对 satisfied 防止漏项，不代替独立复核。

## 目标证明和工具边界收尾

`prove_goal` 必须提交目标版本 `goal_version`、证据版本 `evidence_version` 和验收理由。两个版本分别来自目标与证据的 `node_detail`。任务起点、已作废节点、已归并来源漏洞、推断事实及无 evidence 内容的节点均不能作为证明。证明关系和目标状态原子保存；修改目标会重新开放目标并移除原证明关系。

所有目标验收后进入持久化 `finalizing`：禁止新规划与新领取，正在执行的工具完成后停止当前 Worker。证据和轨迹保留，未开始的遗留工作在完成收尾时标 stopped。收尾前重新核对证明版本；有新增/修改目标或证据失效时恢复 running。用户暂停和已经提交的终态不会被收尾覆盖。任务期限仍由既有超时协调器处理。

无目标、人工直接投放工作时继续沿用既有队列抽干后完成的行为。`goal_met` 不再允许绕过逐项证明。

## 运行中约束和规划反馈

主 Agent、Planner、Worker 的每次模型请求都会附上最新完整约束；工具执行前再次读取，审批等待结束后再核对。约束变化会阻断旧决策批次的所有尚未执行调用，待模型读到新快照再放行。加载失败时阻断。已经执行中的工具保留到边界，规则文本的理解仍依赖模型和既有拦截器。

Planner 可以用 `record_planning_decision` 保存 waiting/no_progress、原因和恢复条件。图、关联证据、约束、漏洞关系、锚定资产没有变化时跳过重复心跳规划；明确用户引导和其它事件仍可以触发规划。可指定 60–86400 秒的复查间隔，在后续心跳时检查；0 表示等待变化。它不会暂停其它可运行工作。

`record_fact.planning_impact` 仅用于解除前置、推翻关键假设或满足目标的关键证据，成功写入后立即通知 Planner。普通观察留空，避免每条事实都造成一次模型规划。漏洞关系进入态势，其中 proposed 仍是假设。

任务结束后，未凑满批次数的漏洞会进行一次自动尾批检查，遵守 enabled、paused、运行去重及 attempted watermark。失败后不会自动重复付费调用，新增漏洞或人工复核才能再次推进。

## 兼容和验证边界

数据库迁移新增 `explorations.planning_state`、意图 waiting 状态和任务 finalizing 状态，启动时幂等执行。工作合同、结果、输入引用和执行代次存储在现有节点 payload；归档恢复同时保留 planning_state 和 round_no。新内置工具按现有目录机制播种，已有工具开关与约束注入开关继续生效；若关闭 complete_intent，新合同工作不能通过正常验收。

回归覆盖数据库事务、并发去重与互斥、依赖调度、旧批次约束阻断、SDK Worker 写事实到验收的完整流程、目标收尾和尾批复核。模拟模型测试只证明执行协议接通；真实模型的规划质量、证据判断能力、Token 成本以及生产环境表现需要另外评测。
