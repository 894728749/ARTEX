# Team execution v2

**Status as of 2026-11-05.** The coordinator owns shared task, queue, assignment, candidate receipt, and review records. A team manager explicitly enqueues work. The dispatcher then matches it to an online, idle device that has the requested role/capabilities and whose owner has task read and execute permission. A queue entry is not an execution authorization by itself. The executor returns a candidate; a different authorized reviewer must review it. Neither submission nor review automatically accepts a finding or completes the task.

## Node configuration

Copy [team-node.example.json](../examples/team-node.example.json) to a private local file and replace placeholder endpoints and paths. For dynamic observation, start from [team-node-runtime.example.json](../examples/team-node-runtime.example.json) and configure a local runtime bridge. These files contain no credentials or usable service addresses. Keep model keys, pairing tokens, and relay secrets in environment variables; the JSON contains only environment-variable names. Do not copy the private node identity state to another device.

`coordinator_url` and `server_name` identify the coordinator for TLS. `lan_addresses` are direct candidates; `relay_url`, room, peer, and `relay_secret_env` describe the fallback route. TLS identity checks apply on both routes. The transport tries LAN first and, while on relay, probes the LAN candidates at HTTP request boundaries. It returns to LAN only after two successful, interval-spaced TLS probes; it closes idle connections so the next request uses LAN, without interrupting an in-flight request. A failed probe leaves traffic on relay. `TransportStatus` exposes the current route, last change time, and latest error to diagnostics.

`work_dir`, `outbox_dir`, and `-state` must be private, absolute locations. The work directory holds assignment material and evidence journals. The durable outbox keeps result receipts until accepted. The node downloads materials in resumable ranges, verifies final size and SHA-256 before exposing them to `read_material`, and verifies cached files before reuse.

### Local commands and MCP tools

`roles`, `models`, `commands`, `mcp_servers`, and `mcp_tools` are device-local policy. An MCP server entry maps a local executable, arguments, and environment allowlist. An MCP tool entry maps a local capability alias to a server name and exact MCP tool name. Add the alias to a role's `capabilities` to allow that role to use it. Remote assignments may request only capabilities advertised for the role; they do not carry local executable paths or model credentials. Reverse static, dynamic, and reviewer roles may use only tools marked `read_only: true`. `read_material` is built in. The reserved `reverse_observe_runtime` is only provided by the dynamic runtime feature.

The executable must be an absolute path to an installed regular file. Allowlist only environment variables needed by that local process; model credential variables are rejected for command and MCP server environments. Tool role filtering and `read_only` are application controls, not an OS sandbox: processes run with the node account's host permissions. Use a dedicated account and OS isolation appropriate to the host.

## Queue and assignment flow

1. Pair a device and run it with its private state file. The node advertises configured roles, capabilities, and, for an authorized dynamic role, runtime profile metadata. The coordinator considers a device online when its recent heartbeat is within the server's online window; active assignments make it unavailable for another assignment.
2. A manager with task manage permission submits an explicit dispatch request to `POST /api/teams/{team}/tasks/{task}/dispatch`. The body uses the assignment fields: `intent_id`, optional `device_id` (`0` or omitted for automatic selection), `capabilities`, `artifact_ids`, `context`, and optional dynamic fields `runtime_profile_id`, `runtime_digest`, `authorize_runtime`. A successful request creates a `queued` record. The dispatcher checks queues about every five seconds and selects a compatible online idle device. Pin `device_id` when the choice must remain on one device; automatic selection waits for a matching candidate.
3. The work view (`GET /api/teams/{team}/tasks/{task}/work`) includes `dispatch_queue` rows with state and `last_error`. Waiting entries remain queued with a reason such as no online compatible device, task not runnable, permission changed, or request became stale. Managers can cancel a queued request with `POST /api/teams/{team}/tasks/{task}/dispatch/{id}/cancel`. A direct assignment endpoint remains available for callers that need immediate assignment creation.
4. Before assignment, the coordinator rechecks task and member permissions, requested role/capabilities, device availability, intent scope, and selected materials. It snapshots the intent contract, constraints, budget, and materials. Changes to task scope or material hashes invalidate a queued request rather than silently changing its meaning. A paused or queued task can wait for dispatch, but the device cannot execute until the task is runnable.
5. The node claims the assignment, downloads and verifies only selected materials, runs the local role, and submits a bounded candidate receipt. Another team member with read and review permission reviews it at `POST /api/teams/{team}/assignments/{assignment}/review`. Self-review is rejected. Accept or reject is recorded as a sourced review and returns the intent to the normal task workflow; it is not itself business acceptance.

Dynamic requests must pin a device and profile and explicitly set `authorize_runtime: true`. The manager selects the materials to authorize. The coordinator binds the selected profile digest and SHA-256 hashes of those materials into the assignment. `runtime_digest`, when supplied, must match the advertised digest; the coordinator records the selected device's current digest. The node accepts the binding only if it matches its own locally configured profile and role allowlist. Each observation is limited by that profile's `max_duration_ms`, and can access only a bound material hash after rechecking the file hash. Dynamic authorization is a one-assignment choice, not a persistent grant. Profiles support Linux, Windows, and Android. The local bridge is launched with only its configured environment allowlist; it must return evidence including the script and artifact hashes plus cleanup state. The node checks cleanup fields before treating an observation as successful.

## Reconnect, evidence, and recovery

`run` keeps retrying transient connection and server failures with bounded exponential backoff; cancellation via context stops the loop. Durable receipts stay in the outbox and are retried with the same assignment epoch and result body. Permanent coordinator rejections are quarantined. `run-once` intentionally exits after one poll/assignment attempt.

Evidence is appended and fsynced after each tool call. A durable `execution.started` fence prevents replay after a process restart. If the process stops after that marker, the node submits a blocked checkpoint with recoverable journal entries (a partial final line may be omitted); operators should review the journal and explicitly re-dispatch if appropriate. This avoids repeating side effects. Gentle task pause stops after the current bounded tool, records evidence, and sends a checkpoint. Assignment authorization and lease/epoch checks are refreshed before tool activity.

## Cold archive and read-only team history

Team assignments, sharing/resources, candidate evidence, reviews, and identity provenance are preserved as read-only task history in a cold archive and exposed after restore by `GET /api/teams/{team}/tasks/{task}/history`. History snapshots retain source names and original IDs for audit even if those identities do not exist in the restored environment. Restore does not recreate active assignments, execution leases, old device tokens, membership, sharing grants, permissions, or runtime authorization. Existing local team permissions remain as they were in that environment. Users must explicitly share/authorize and dispatch new work there. Restored history is evidence of prior activity, not an active grant or verified authorization in the current environment.

## Acceptance scope and limitations

- The implementation includes queue matching, locally mapped MCP tool policy, dynamic profile/material binding, reconnect/outbox retries, resumable material staging, LAN recovery probing, and archived read-only team history.
- Windows, Linux, and Android runners were validated during this review with the project's owned samples, including actual observation and cleanup. The node end-to-end run was tested separately with a local fake OpenAI-compatible model. These results are distinct: there has not been a test with a second real physical device. This guide does not claim cross-machine or production acceptance.
- Device OS permissions remain an important boundary: local commands, MCP servers, and runtime bridges run under the node account. Their configured roles and read-only labels do not replace operating-system isolation.
